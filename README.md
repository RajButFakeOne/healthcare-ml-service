# Healthcare consultation-duration model: live service

Hosted version of `ml_model/` from the app. It predicts consultation minutes in real time
and **learns from every appointment the moment it ends**.

```
Doctor taps "Complete"  ->  appointments.status = 'Completed'
        |                         (consultation_start / consultation_end saved)
        v
Supabase trigger  --POST /train-->  Render service: duration = end - start
                                    -> model updates in ~5 ms, next /predict uses it
Flutter booking   --POST /predict-> instant estimate (falls back to the offline model)
```

A background loop also re-reads completed appointments from Supabase every 10 minutes and learns
any it missed (e.g. webhook sent while the service was waking up). Every appointment is
learned **once**. After a restart the model rebuilds itself from the seed data plus all
completed appointments in Supabase.

## Deploy (about 10 minutes)

1. **Push this folder to a GitHub repo.**
2. **Render** -> New -> Blueprint -> pick the repo. When prompted, paste `SUPABASE_SERVICE_KEY`
   (Supabase -> Project Settings -> API -> `service_role`; keep it secret, never put it in the app).
   Render auto-generates `WEBHOOK_SECRET`; copy its value from the service's Environment tab.
3. **Supabase SQL Editor**: open `supabase/ml_webhook.sql`, run STEP 1 (secret), set your
   `https://<service>.onrender.com/train` URL, then run STEP 2.
4. **Flutter**: copy `flutter_changes/` over the app (`changes.diff` shows exactly what changed),
   set the URL in `lib/config/ml_config.dart` (or `--dart-define=ML_API_URL=...`), `flutter pub get`.
5. **Check it works**: `curl https://<service>.onrender.com/health`, complete a test appointment
   in the app, then `curl .../metrics` and watch `real_samples` go up by one.

## API

| Endpoint | Auth | Purpose |
|---|---|---|
| `POST /predict` `{symptom, age?, queue_serial?}` | none | minutes + `model_version` |
| `POST /predict/batch` `{items:[...]}` | none | many predictions in one call |
| `POST /train` | `X-Webhook-Secret` | learn from one finished appointment |
| `POST /admin/reconcile?full=true` | `X-Webhook-Secret` | force a catch-up from Supabase |
| `GET /health`, `GET /metrics` | none | status, counts, live accuracy |

`live_mae_minutes` in `/metrics` is measured on real appointments *before* the model learns from them
(test-then-train), so it is an honest read of how well the model fits your clinic.

## Things worth knowing

- **The starting data is synthetic** (generated by `generate_and_train.py`). Real visits are weighted
  3x (`REAL_SAMPLE_WEIGHT`) so the model adapts faster, but expect predictions to settle only after a
  few dozen real appointments per common symptom. Watch `live_mae_minutes`.
- **Bad durations are ignored** (< 2 min or > 90 min, or end before start), e.g. a doctor who forgot to
  press End. Otherwise one 9-hour row would distort every prediction.
- **Run exactly one instance.** The model lives in memory; the Dockerfile and blueprint pin 1 worker/1 instance.
- **Free plan sleeps after 15 min idle** (30-60 s cold start). The app handles this by timing out after 6 s
  and using the offline model, and the reconcile loop recovers any missed webhook, but `starter` avoids it.
- **Privacy:** symptom text, age and appointment timestamps leave Supabase for Render. That is health-related
  data, so check this fits your hospital's data-protection obligations. `/predict` is open (the app can't
  keep a secret); it takes no names or IDs.
